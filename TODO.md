# GentX2 delivery outcomes

- [ ] **Stripe Projects and application foundation.** Build GentX2 using Next.js App Router, TypeScript, Tailwind CSS, shadcn/ui, Supabase Postgres/Auth/Realtime/Storage, the CreateOS TypeScript SDK (`@nodeops-createos/sandbox`), and a server-side configurable model provider for BlackHat, WhiteHat, Sentinel, Auditor, and Orchestrator. Integrate Stripe Projects according to the official instructions; do not add Stripe Payments unless specifically needed. Use Stripe Projects to set up requested services in the existing project, inspect resource plan/spend before provisioning or upgrading, and never make an unapproved payment. Keep all API keys server-side. Supply `.env.example` placeholders only and README setup/migration commands, architecture notes, threat model, and deployment guidance. Do not seed user, project, or target records.

- [ ] **Supabase authentication, schema, artifacts, and authorization.** Use Supabase for projects, scans, findings, agent runs, patch metadata, audit events, and optional Realtime updates. Create schema and migrations for `profiles`, `projects`, `project_members`, `scans`, `agent_runs`, `findings`, evidence/artifacts metadata, `patches`, `verification_runs`, and `audit_events`. Enable and test RLS for every user-owned table. Enforce least privilege with RLS and test cross-user isolation. Add server-side authorization checks in addition to RLS. Store large artifacts in private Storage buckets with strict authorization and retention. Keep privileged keys out of the browser and sandbox.

- [ ] **Target intake, normalization, authorization, and scope.** Support folder/ZIP upload, GitHub repository, and deployed website URL. Normalize each into one common target record. Require explicit authorization and scope. For folder/repository modes, operate on an isolated working copy and provide downloadable patches; for URL-only mode, perform authorized black-box testing and report remediation guidance unless source access is explicitly supplied. Validate redirects and every resolved IP; restrict egress to the authorized network scope; block localhost/private/link-local/metadata targets unless explicitly required for a locally isolated test; revalidate DNS and redirects to prevent SSRF and rebinding. Treat target content as untrusted data and defend against prompt injection.

- [ ] **Verified CreateOS execution and lifecycle safety.** Use CreateOS sandboxes for all untrusted target code, generated code, builds, tests, and security-tool execution. Inspect official documentation and the installed SDK's actual methods; run a real sandbox smoke test before claiming the adapter works. Configure environment variables for CreateOS and the model provider and keep every API key server-side. Never expose privileged keys to the browser or sandbox. Configure and verify scoped network egress before running untrusted code. Apply CPU, memory, time, output, request, round, and model-cost limits. Protect credentials, prevent BlackHat, WhiteHat, Sentinel, Auditor, or Orchestrator from modifying the verifier or trusted policy, stop and clean up sandboxes reliably, and never claim an integration works until it has been verified.

- [ ] **Provider and five distinct named roles.** Configure `AGENT_API_KEY` and `AGENT_MODEL` through protected environment inputs; keep the provider server-side. Use structured JSON output and Zod validation. Verify BlackHat, WhiteHat, Sentinel, Auditor, and Orchestrator role contracts before claiming the provider works. Review the selected provider's data handling policy before sending target evidence. BlackHat discovers and reproduces authorized vulnerabilities; WhiteHat proposes patches and regression tests; Sentinel independently verifies findings and fixes; Auditor reviews diffs, build/lint/security-test results; Orchestrator coordinates permissions, budgets, state transitions, retries, rounds, and stop conditions. These five named roles may share the same model but must have separate system prompts, structured outputs, contexts, permissions, and budgets. Implement resilient provider adapters, retries with bounded backoff, timeouts, token/cost accounting, structured error handling, and idempotent job/state transitions. Do not make unsupported claims about model capabilities or free-tier availability.

- [ ] **Trusted autonomous workflow, scanners, and human controls.** Implement the workflow: authorization and scope validation → sandbox creation → BlackHat scan → exploit reproduction → Sentinel verification → WhiteHat patch → Auditor diff/build/lint/regression/security checks → Sentinel replays original exploit and verifies legitimate behavior → accept or rollback → next round. Use OWASP ZAP Automation Framework and optional Nuclei only where installation, licensing, authorization, and safe configuration are verified; never run broad scans against arbitrary targets. BlackHat, WhiteHat, Sentinel, Auditor, and Orchestrator must never alter verification criteria, fabricate evidence, modify trusted orchestration policy, or self-approve fixes. Require human approval before exporting or applying patches. Implement rollback, cancellation, emergency stop, no automatic deployment, and human approval before exporting or applying patches. Inconclusive, failed, or skipped checks must never count as clean rounds. Default to three consecutive fully verified clean rounds, configurable in trusted policy: no new verified findings, passing regression tests, unsuccessful replay of previous exploits, and successful independent verification. Never claim that clean rounds prove the absence of all vulnerabilities.

- [ ] **Immutable audit, evidence, persistence, and live updates.** Include an append-only audit trail for BlackHat, WhiteHat, Sentinel, Auditor, and Orchestrator, with timestamps, actor, action, input/output hashes where practical, tool results, evidence references, and explicit state transitions. Persist session history, findings with severity/confidence/evidence, role runs, patch metadata, verification runs, artifacts metadata, and final reports. Use SSE or Supabase Realtime for actual streamed events; every dashboard state and log must reflect real backend events, never fabricated activity. Use private Storage authorization and retention for large artifacts. Clearly distinguish completed, failed, skipped, inconclusive, and partial results.

- [ ] **Cyber-operations dashboard.** Provide project selection, new scan workflow, target scope/authorization confirmation, live cards for BlackHat, WhiteHat, Sentinel, Auditor, and Orchestrator, streaming event log via SSE or Supabase Realtime, findings with severity/confidence/evidence, patch diff viewer, test results, sandbox resource status, round timeline, scan history, settings, and emergency stop. Design a polished high-end cyber operations terminal with near-black background, neon-green terminal accents, cyan highlights, subtle scanlines, monospace typography, restrained red warnings, responsive layout, and accessible contrast. Display BlackHat and WhiteHat prominently side by side; show Sentinel, Auditor, and Orchestrator in distinct glowing panels; include real-time terminal logs, vulnerability evidence, animated attack-and-defense status indicators, code diffs, sandbox health, round progression, emergency-stop controls, and a final report. Keep it sleek, readable, responsive, professional, and not cluttered or overly game-like. Include loading, empty, error, cancellation, and partial-failure states. All status indicators and logs must reflect actual backend events.

- [ ] **Tests and safe delivery guidance.** Add unit tests for orchestration and authorization, integration tests for database policies and model adapters, and CreateOS sandbox smoke tests. Run tests incrementally, never silently skip a failed check, and clearly report any integration blocked by external credentials, capacity, cost, or service limits. Provide migration commands, architecture notes, threat model, and deployment guidance. Do not automatically deploy patches or target modifications.
